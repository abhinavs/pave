# Production readiness

A honest checklist of what is done, what is partial, and what is missing
before Pave is "production ready" in the strict sense (a stranger could
ship the template to a paying-customer workload without inheriting a known
hazard).

The bar here is *single-VPS production*, not *FAANG-scale*. Pave is
deliberately not Kubernetes; the gaps below are the ones that matter at
that scale, not the ones that only matter past it.

---

## Done

These are in the repo today and exercised end-to-end.

- **Process supervision.** Gunicorn under systemd (`deploy/pave-api.service`),
  Soniq worker under systemd (`deploy/pave-worker.service`). Both restart
  on crash and are tied to the symlink-flipped release directory.
- **Reverse proxy + TLS.** `deploy/nginx.conf` terminates TLS and proxies
  to the gunicorn socket; `fab setup-tls` issues the Let's Encrypt cert.
- **Atomic deploys with rollback.** `fab production deploy` writes to a new
  `releases/{ts}-{sha}` directory, flips `current`, restarts services, and
  rolls back automatically if `/health` does not return `{"status":"ok"}`
  within the retry window.
- **Schema-checked configuration.** Every setting has three homes
  (`.env.example`, `.env.schema`, `app/settings.py`). Missing required
  settings fail fast at Pydantic startup.
- **Database migrations.** Alembic, autogenerated migrations, downgrade
  step verified per migration. Migrations run on the server before the
  symlink flip.
- **Auth fundamentals.** bcrypt password hashing, DB-backed sessions with
  per-device revocation, OAuth (Google, GitHub), email verification,
  password reset that revokes all sessions on success, fingerprint-bound
  reset tokens (a token cannot be replayed after the reset it authorised).
- **Rate limiting.** `slowapi` on `/auth/login` (5/min), `/auth/forgot`
  (5/min), `/auth/resend` (3/min).
- **Security headers + cookies.** SessionMiddleware secret-keyed, Secure
  cookie flag bound to `not DEBUG`, HTTPS-only redirects via Nginx, CSRF
  middleware in non-debug, request-id middleware on every response.
- **Observability surface.** Structured logs via structlog, request ids,
  optional Sentry, opt-in Prometheus metrics (off by default - exposing
  /metrics on the public surface needs an explicit choice).
- **Offline job queue.** Soniq with two real jobs (`process_payload`,
  `send_verification_email`), retried with exponential backoff for the
  email job.
- **Backups + integrity.** `fab backup` pipes `pg_dump` to gzip, then runs
  `vrk digest --algo sha256 --file <path> --compare` so a corrupted dump
  is caught on the next backup run, not on the day you need to restore.
  `fab restore` re-checks the digest before piping into psql.
- **Host hardening.** One-shot Fabric tasks for ufw, fail2ban, certbot,
  unattended upgrades, swap, journald log capping, and password+root SSH
  lockdown (run last, on purpose).
- **CI.** GitHub Actions for lint/typecheck/test, an external health probe
  on a 10-minute cron, and a tag-driven release pipeline that pins the
  artifact with `vrk digest`.
- **Deploy-event sink.** `WEBHOOQ_ENDPOINT` receives a `deploy.success`
  event after a green health check.

## Partial - works, but needs more before a strict prod ship

These are present but would not pass an external readiness review without
follow-up.

- **No staging parity.** `fab staging` exists as a target but there is no
  contract that a deploy ships through staging before production. A blue/
  green or staged rollout would catch the cases the health probe misses.
- **Single-instance only.** One VPS, one app process group. Failover is
  manual - DNS flip, fresh deploy. Fine for early stages; not for a SLA.
- **No outbound retries on Webhooq emission.** The deploy event is
  best-effort and silently swallowed on failure. Acceptable today; would
  need a small retry queue if the event becomes load-bearing.
- **No tracing.** structlog gives correlated logs via the request id, but
  there is no OpenTelemetry span surface. Add `opentelemetry-instrumentation-fastapi`
  if you need distributed traces.
- **Avatar storage is local-disk.** `AVATAR_DIR` defaults under the served
  static tree; production should mount it *outside* the release directory
  (so a deploy does not erase uploads). This is documented but not enforced.
- **No automated dependency upgrades.** Add Dependabot or Renovate for
  `requirements.txt`, GitHub Actions versions, and the Tailwind binary
  pin. Unattended upgrades on the host covers the OS side.
- **Soniq DLQ not configured.** Retries cover transient failures, but a
  job that fails permanently currently exhausts retries and disappears
  into logs. A dead-letter queue plus an alert is a one-day add.
- **No CSP.** Content-Security-Policy is not set. With HTMX and inline
  scripts in `base.html`, this needs a careful pass before turning it on.
- **Backups are local-disk.** `fab backup` writes under `/srv/pave/backups`.
  For a real ship the backup script should push to S3 (or rclone-equivalent)
  off-host, and `setup-backups` should configure that.
- **No SAST / dependency-vuln gate in CI.** Add `pip-audit` and `ruff` (
  already there) to the gate; consider `gitleaks` for secret scanning.

## Missing - decide before shipping

These are conscious omissions or explicit "you will need this if".

- **No multi-tenant scoping.** Pave assumes one logical app per database.
  Bolt this on at the model layer; do not retrofit it at the middleware
  layer.
- **No GDPR/erasure plumbing.** No "delete my data" endpoint, no audit log
  of who touched a user record. If the app collects EU resident data,
  this is a hard gap.
- **No admin UI.** There is no `/admin`. Use `pave shell` (IPython) plus
  psql until you have a reason to build one - then build the smallest
  thing that solves the actual problem, not a CMS.
- **Email deliverability.** The generic HTTP provider is provider-neutral
  but does nothing for DKIM / SPF / DMARC. Configure those on the sending
  domain before sending anything that matters.
- **Secret rotation.** `SECRET_KEY` rotation invalidates every session
  cookie at once - acceptable, but document the playbook. OAuth client
  secrets and email API keys have no rotation tooling.
- **Load testing.** No `locust` or `k6` artefacts. The Gunicorn worker
  count in `deploy/` is the upstream default; tune it against a real
  workload before relying on it.
- **Compliance posture.** No SOC2/HIPAA/PCI controls. Pave is not the
  right starting point for any of those without dedicated work.

## Recommended next steps, in order

If the question is "what should I do this week to move this from a
template to a real production app", the order I would pick:

1. **Configure off-host backups** (S3 + lifecycle policy, plus a monthly
   restore drill). Backups that nobody has restored are not backups.
2. **Add a DLQ + alert for Soniq.** The first job that fails permanently
   in production should page someone, not vanish.
3. **Set up Dependabot or Renovate.** Pinned deps that nobody upgrades
   are a known-vuln waiting room.
4. **Add `pip-audit` to CI.** One step in `ci.yml`; fails the build if a
   known CVE in a runtime dep is unpatched.
5. **Document and test the rotation playbook** for `SECRET_KEY`, OAuth
   secrets, and the email API key.
6. **Write a load test.** k6 or locust against a staging copy of
   production, sized to expected peak * 3. Tune Gunicorn worker count
   from the result, not from a guess.
7. **Decide CSP.** Either turn it on (and accept the work to harden the
   templates) or write down the explicit reason you are not.

After those seven, Pave is "I would ship this to my own customers" ready.
