# Database migrations

Pave uses Alembic for schema migrations. This page covers the day-to-day
workflow and the operational rules that keep production deploys safe.

The single most important rule is at the bottom of the next section, so read
to the end before you ship anything: at deploy time, the old release is still
serving traffic when the new migration runs. Every migration must be
backward-compatible with the previous release's code.

## The 30-second version

```bash
pave migration --message "add users table"   # generate
$EDITOR alembic/versions/000X_add_users_table.py   # review (always)
pave migrate                                  # apply locally
pave downgrade && pave migrate                # confirm the downgrade works
git add alembic/versions/ && git commit       # ship it
```

You should see:

```
INFO  [alembic.runtime.migration] Running upgrade 0003 -> 0004, add users table
```

If `pave migrate` printed nothing, you forgot to commit the version file or
the head is already current. Run `alembic current` to check.

## Generating a migration

After editing or adding a model under `app/models/`, generate a revision:

```bash
pave migration --message "add referral_code to users"
```

This calls `alembic revision --autogenerate -m "..."` and writes a new file
under `alembic/versions/`. The message becomes part of the filename, so keep
it short, descriptive, and in lowercase imperative form:

- Good: `add users table`, `make user.email unique`, `add index on webhook_events.slug`
- Bad: `Migration`, `WIP`, `fix stuff`, `Added Users Table.`

Alembic prefixes the file with a hash. Pave's existing migrations use a
zero-padded sequence (`0001_`, `0002_`, `0003_`) because they were hand-written
during the bootstrap phase. New autogenerated migrations will use Alembic's
hash; that is fine, do not rename them.

## Reviewing the generated file

Always open the generated file before you run `pave migrate`. Autogenerate is
a draft, not a finished migration. It misses or gets wrong:

- Column type changes (e.g. `String(255)` to `String(320)`)
- Check constraints
- PostgreSQL-specific types (`JSONB`, `ARRAY`, enums, `tsvector`)
- `server_default` values, especially anything wrapped in `sa.text(...)`
- `JSON` columns when your local DB is SQLite (SQLite has no native JSON type)
- Renames: Alembic sees a rename as a drop plus an add, which loses data

Read both `upgrade()` and `downgrade()`. The downgrade is the half that gets
skipped in review and bites you later. A correct downgrade looks like the
upgrade run in reverse:

```python
def upgrade() -> None:
    op.add_column("users", sa.Column("referral_code", sa.String(32), nullable=True))
    op.create_index("ix_users_referral_code", "users", ["referral_code"], unique=True)


def downgrade() -> None:
    op.drop_index("ix_users_referral_code", table_name="users")
    op.drop_column("users", "referral_code")
```

The pattern Pave's existing migrations follow (see `alembic/versions/0002_add_users.py`)
is worth copying: `sa.Uuid()` for IDs, `sa.text("CURRENT_TIMESTAMP")` for
timestamp defaults, plain `sa.JSON()` for JSON. That DDL is portable to the
SQLite database used in tests, which matters because the test suite runs
migrations on SQLite, not Postgres.

## Applying locally

```bash
pave migrate
```

You should see:

```
INFO  [alembic.runtime.migration] Running upgrade <prev> -> <new>, <message>
```

Then test the downgrade. This is non-optional:

```bash
pave downgrade           # rolls back one revision
# inspect the DB: psql, pave console, whatever you like
pave migrate             # forward again
```

If `pave downgrade` errors, or the table looks wrong afterwards, fix the
`downgrade()` function before committing. A migration without a working
downgrade is a half-written migration.

`pave downgrade` defaults to `-1` (one step). Pass an explicit target to go
further: `pave downgrade -3` or `pave downgrade base`.

## The zero-downtime rule

Pave deploys are release-directory style with a `current` symlink:

```
releases/
  20260520-120000-abc123/
  20260521-093000-def456/      <- current  ->  here
  20260527-150000-ghi789/      <- new release, prepared but not live yet
```

`fab deploy` (see `fabfile.py`) does this, in order:

1. rsync the new code to a fresh release directory
2. create a venv, install requirements
3. run `alembic upgrade head` from the new release directory
4. flip the `current` symlink to the new release
5. restart `pave-api` and `pave-worker`
6. health-check; on failure, flip back automatically

Steps 3 and 4 are the dangerous ones. Between them, the migration has already
run against production, but the running gunicorn workers are still serving
from the **old** release. There is a window, usually a few seconds, where:

```
   time -->
   [old code serving traffic .................][new code serving traffic ...]
                                ^               ^
                                |               |
                                migration       symlink flip + restart
                                already ran     happens here
```

During that window, the old code must continue to work against the new
schema. This is why migrations have to be additive, and why the rules below
exist.

If a migration fails in step 3, the symlink never flips and the old release
keeps serving. That is the safe outcome. The bad outcome is a migration that
succeeds but is incompatible with the old code; deploy keeps going, the
symlink flips, and in the meantime the old workers throw 500s on every
request that touches the changed table.

## The additive-only pattern

For anything destructive (drop a column, rename a column, change a NOT NULL
constraint to required), split the work across three deploys. Renaming
`users.name` to `users.full_name` is the canonical example:

**Deploy 1: add the new column, backfill, keep both.**

```python
def upgrade() -> None:
    op.add_column("users", sa.Column("full_name", sa.String(255), nullable=True))
    op.execute("UPDATE users SET full_name = name WHERE full_name IS NULL")
```

App code still reads and writes `name`. The new column exists but is unused
by the application. Old release works. New release works. Rollback works.

**Deploy 2: switch the code to the new column. Leave both columns in the
database.**

```python
# app/models/user.py
class User(Base):
    full_name: Mapped[str] = mapped_column(String(255))
    # name still exists in the DB, no longer mapped
```

No migration in this deploy, or a tiny one that adds NOT NULL on `full_name`
once you have confirmed the backfill is complete. Both releases now write to
`full_name` consistently. The old `name` column is dead weight, but harmless.

**Deploy 3: drop the old column.**

```python
def upgrade() -> None:
    op.drop_column("users", "name")
```

By now, no live code touches `name`. Dropping it is safe.

Each of the three deploys is independently reversible. If deploy 2 misbehaves,
you can roll back to deploy 1 and the database is still consistent.

The rule that makes this work, stated negatively: **do not drop or rename a
column in the same deploy as the code change that uses the new name.** If you
catch yourself writing a migration that drops a column, check that the code
referencing that column was removed in a previous deploy, not this one.

## Data migrations vs schema migrations

Schema migrations belong in Alembic. Data migrations belong in a one-shot
script you run with `pave console`.

Small backfills inline in an Alembic file are fine:

```python
def upgrade() -> None:
    op.add_column("users", sa.Column("full_name", sa.String(255), nullable=True))
    op.execute("UPDATE users SET full_name = name WHERE full_name IS NULL")
```

Anything more complex (fan-out, external API calls, conditional logic across
millions of rows) is harder to roll back, harder to retry, and harder to test
than a script:

```python
# scripts/backfill_full_name.py
import asyncio
from sqlalchemy import select
from app.database import AsyncSessionLocal
from app.models.user import User


async def main() -> None:
    async with AsyncSessionLocal() as db:
        users = (await db.execute(select(User).where(User.full_name.is_(None)))).scalars()
        for u in users:
            u.full_name = u.name
        await db.commit()


if __name__ == "__main__":
    asyncio.run(main())
```

Run it once: `pave console` then `exec(open("scripts/backfill_full_name.py").read())`,
or run it as a standalone script after deploy. Keep the file in `scripts/`
and delete it once the backfill is done and committed somewhere durable.

## How migrations run in production

You do not run them. `fab deploy` does, inside the new release directory,
before the symlink flips:

```python
with conn.cd(release_path):
    conn.run("python -m venv .venv")
    conn.run(".venv/bin/pip install -q -r requirements.txt")
    conn.run(".venv/bin/alembic upgrade head")

conn.run(f"ln -sfn {release_path} {CURRENT}")
conn.run("sudo systemctl restart pave-api pave-worker")
```

You should see, in the deploy output:

```
INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.
INFO  [alembic.runtime.migration] Will assume transactional DDL.
INFO  [alembic.runtime.migration] Running upgrade 0003 -> 0004, add users table
```

If `alembic upgrade head` fails, the deploy stops there. The symlink does not
flip and the old release keeps serving traffic. No partial state, no panic.

Do not SSH in and run `alembic upgrade head` by hand. That bypasses
`fab validate`, runs from an arbitrary directory, and creates a window where
the running code does not match the schema. If you need to inspect the live
DB, use `fab psql`.

## Rolling back

`fab rollback` flips the `current` symlink to the previous release directory
and restarts the services. It does **not** undo migrations:

```bash
fab rollback
```

You should see:

```
rolled back to /srv/pave/releases/20260521-093000-def456
```

Schema rollback is a separate manual step, and most of the time you should
avoid it. If migration N broke something, the usual fix is to write migration
N+1 that corrects it, then deploy that. That is what the additive pattern is
for: each migration in the chain is small enough that you can fix forward.

If you genuinely need to undo a schema change, SSH in, drop into the release
directory that has the migration file, and run `.venv/bin/alembic downgrade -1`.
This is rare and should be done with a human watching the database. Open a
psql session in another terminal first.

## Merging divergent heads

If two PRs both generated migrations from revision `0005`, you end up with
two `0006_*` files in the alembic versions directory. Alembic will refuse to
run with this error:

```
ERROR [alembic.util.messaging] Multiple head revisions are present for given
argument 'head'; please specify a specific target revision
```

Fix it with a merge revision:

```bash
alembic merge -m "merge migration heads" <revision_a> <revision_b>
pave migrate
```

You should see a new merge file in `alembic/versions/` with both parents in
its `down_revision` tuple. Commit it in the PR that is being rebased on top
of the other. Do not try to fix this by editing `down_revision` by hand.

## Common mistakes

These are the ones that keep showing up:

- **Dropping a column in the same deploy as the code that stopped writing to
  it.** Breaks the old release during the symlink window. Use the three-deploy
  pattern.
- **Forgetting to review the autogenerated file.** Alembic happily generates
  a migration that drops every table that does not appear in `Base.metadata`,
  which is what happens if you forgot to import a new model in
  `app/models/__init__.py`. Always read upgrade and downgrade before you
  commit.
- **Postgres-specific types that fail on SQLite.** `JSONB`, `ARRAY`, native
  `ENUM`. The test suite runs migrations on SQLite, so the test run is the
  first place this will blow up. Prefer `sa.JSON()`, `sa.String()` with a
  check constraint, etc. If you genuinely need a Postgres type, gate it on
  dialect inside the migration.
- **Server defaults that only get evaluated on Postgres.** `sa.text("gen_random_uuid()")`
  works on Postgres and fails on SQLite. Pave's convention is `sa.text("CURRENT_TIMESTAMP")`
  for timestamps and application-side UUID generation for primary keys.
- **Renaming a column with `op.alter_column(..., new_column_name=...)`.**
  Works fine locally and breaks the old release in production during the
  symlink window. Use the additive pattern instead.
- **Not committing the migration file.** `pave migrate` works on your
  machine, your PR passes review, the deploy fails because the file is not
  in git. `git status` after every `pave migration` call.
- **Editing a migration after it has been applied somewhere.** If the
  migration ran in CI, on staging, or on a teammate's machine, the
  `alembic_version` table now points at its revision id. Edit the file and
  the histories diverge. Once a migration is merged, treat it as immutable
  and fix forward.
